## 12. Rollback and data-safety limits

- Both migrations use explicit transactions; a failing statement before COMMIT should roll back that migration's DDL and its bucket-row insert. This is not a successful-deployment down migration: no down scripts exist, and a committed migration is not automatically reversible.
- Candidate status/amount constraints are replaced/expanded and validated; the migrations do not normalize existing booking/task rows. If a later application writes newly allowed status values, restoring the old constraints can fail or reject live rows. The README's normalization claim must not be used as a rollback plan.
- `lawyers.experience`, `bookings.idempotency_key`, wallet ledger/idempotency rows, review changes, Auth/profile links, and any Storage objects written after deployment could carry data that would be lost or misinterpreted by a reverse DDL. Preserve and reconcile it; prefer a reviewed forward corrective migration.
- The bucket is private and inserted only if absent, then checked. After a successful commit it must not be dropped blindly; object data and metadata may exist even though the initial migration created no object rows. Preserve files and verify retention before any bucket rollback.
- Auth confirmation trigger changes can create profiles and explicit mappings; do not delete Auth users/profiles or relink by email as a rollback. Reconcile UID/email mapping with verified evidence and an audit log.
- Financial rows are not safely reversible by schema rollback. Reconcile ledger entries against trusted provider events and keep credits/paid entitlement disabled until verified settlement exists.
- Restoring the old blanket grants/policies would re-open confirmed security defects. Do not roll back to the unsafe policy set merely to make an old client work; keep Express available or use a reviewed forward fix.
- `service_role` bypasses RLS. Keep its key only in trusted server environments, and audit all service-role calls separately from authenticated/anon policy tests.
